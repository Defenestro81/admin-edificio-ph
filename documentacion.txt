────────────────────────────────────────────────────────────────────────────────
1. DESCRIPCIÓN GENERAL
────────────────────────────────────────────────────────────────────────────────

Sistema web de administración de un edificio de propiedad horizontal.
Permite gestionar las unidades, calcular las expensas mensuales, registrar
pagos, hacer seguimiento de deudas por unidad y enviar liquidaciones por mail.

Tecnología:
  - Frontend : HTML5 + CSS3 + JavaScript vanilla (SPA de un solo archivo)
  - Backend  : PHP 7.4+ con PDO
  - Base de datos: MySQL (via XAMPP)
  - Email    : PHPMailer + Gmail SMTP
  - URL local: http://localhost/edificio/

3. CONFIGURACIÓN INICIAL
────────────────────────────────────────────────────────────────────────────────

Archivo: .env  (en la raíz del proyecto, fuera del repositorio)
Plantilla: .env.example  (sí está en el repositorio, sin datos reales)

  DB_HOST=localhost
  DB_USER=edificio
  DB_PASS="..."
  DB_NAME=edificio

  MAIL_HOST=smtp.gmail.com
  MAIL_PORT=587
  MAIL_USER=...        → cuenta de Gmail remitente
  MAIL_PASS="..."      → contraseña de aplicación de Google
  MAIL_FROM=...
  MAIL_FROM_NAME="..."

includes/config.php lee el .env al arrancar y define las constantes
DB_HOST, DB_USER, DB_PASS, DB_NAME, MAIL_* que usa el resto del código.
Si el .env falta o le falta una clave, corta con un error 500 explícito.
El .htaccess de la raíz bloquea el acceso web al .env y a los .sql.

Para instalar:
  1. Iniciar XAMPP (Apache + MySQL)
  2. Abrir phpMyAdmin → ejecutar Deploy base de datos/database.sql
  3. Copiar .env.example como .env y completar los datos correctos
  4. Acceder a http://localhost/edificio/

4. BASE DE DATOS
────────────────────────────────────────────────────────────────────────────────

Nombre: edificio

TABLA: unidades
  id            INT PK AUTO_INCREMENT
  nombre        VARCHAR(100)        Ej: "Piso 1°", "PB + Complementario"
  propietario   VARCHAR(150)
  email         VARCHAR(150)        Para envío de liquidaciones
  coeficiente   DECIMAL(8,6)        Porcentaje fiscal (suma total debe = 1.0000)
  ascensor      TINYINT(1)          1 = usa ascensor, 0 = no
  orden         INT                 Orden de visualización
  creado_en     DATETIME

TABLA: gastos_fijos
  id            INT PK
  concepto      VARCHAR(150)        Ej: "EDEA", "Seguro Edificio"
  importe       DECIMAL(12,2)
  division      ENUM('coeficiente','partes_iguales')
  activo        TINYINT(1)          El DELETE es lógico (activo=0)
  creado_en     DATETIME

TABLA: gastos_fijos_unidades
  gasto_fijo_id INT  FK → gastos_fijos.id
  unidad_id     INT  FK → unidades.id
  PK compuesta (gasto_fijo_id, unidad_id)
  → indica a qué unidades aplica cada gasto fijo

TABLA: gastos_esporadicos
  id            INT PK
  periodo       CHAR(6)             YYYYMM (ej: "202605")
  concepto      VARCHAR(150)
  importe       DECIMAL(12,2)
  division      ENUM('coeficiente','partes_iguales')
  creado_en     DATETIME

TABLA: gastos_esporadicos_unidades
  gasto_esporadico_id INT  FK → gastos_esporadicos.id
  unidad_id           INT  FK → unidades.id

TABLA: liquidaciones
  id            INT PK
  periodo       CHAR(6)             YYYYMM
  tipo          ENUM('ordinaria','extraordinaria') DEFAULT 'ordinaria'
  titulo        VARCHAR(150)        Motivo (solo extraordinarias)
  calculada_en  DATETIME
  total_general DECIMAL(14,2)
  → periodo YA NO es UNIQUE a nivel de BD: solo puede haber una liquidación
    'ordinaria' por período (lo garantiza el código en api/liquidacion.php,
    que borra la anterior antes de insertar), pero puede haber varias
    'extraordinaria' en el mismo período. Índice: (periodo, tipo).

TABLA: liquidacion_detalle
  id               INT PK
  liquidacion_id   INT  FK → liquidaciones.id
  unidad_id        INT  FK → unidades.id
  total            DECIMAL(12,2)   Total a cobrar a esa unidad ese período
  mail_enviado     TINYINT(1)
  mail_enviado_en  DATETIME

TABLA: liquidacion_lineas
  id          INT PK
  detalle_id  INT  FK → liquidacion_detalle.id
  concepto    VARCHAR(150)
  importe     DECIMAL(12,2)
  tipo        ENUM('fijo','esporadico','extraordinario')

TABLA: caja
  id          INT PK
  fecha       DATE
  tipo        ENUM('ingreso','egreso')
  concepto    VARCHAR(200)
  unidad_id   INT  FK → unidades.id  ON DELETE SET NULL  (puede ser NULL)
  importe     DECIMAL(12,2)
  periodo     CHAR(6)   YYYYMM — período al que imputa el pago (puede ser NULL)
  notas       TEXT
  creado_en   DATETIME

TABLA: cuenta_corriente
  id              INT PK
  unidad_id       INT  FK → unidades.id
  periodo         CHAR(6)              YYYYMM
  deuda           DECIMAL(12,2)        Total liquidado ORDINARIO del período
  saldo_anterior  DECIMAL(12,2)        Saldo arrastrado del período anterior
  extraordinario  DECIMAL(12,2)        Suma de cargos de liquidaciones extraordinarias
  pagado          DECIMAL(12,2)        Suma de ingresos de caja imputados
  saldo_final     DECIMAL(12,2) GENERATED ALWAYS AS (saldo_anterior + deuda + extraordinario - pagado) STORED
  cerrado         TINYINT(1)
  UNIQUE KEY (unidad_id, periodo)

  → 'deuda' y 'extraordinario' se actualizan de forma independiente:
    recalcular la liquidación ordinaria SOLO pisa 'deuda' (nunca toca
    'extraordinario'), y emitir/anular una extraordinaria SOLO suma o
    resta sobre 'extraordinario' (nunca toca 'deuda'). Así ninguna de
    las dos operaciones puede borrar el trabajo de la otra.


────────────────────────────────────────────────────────────────────────────────
5. API — ENDPOINTS
────────────────────────────────────────────────────────────────────────────────

Todas las respuestas son JSON con formato:
  { "ok": true,  "data": ... }
  { "ok": false, "error": "mensaje" }

Todos los POST y PUT reciben el body como JSON (Content-Type: application/json).

──────────────────────────────────────
5.1 UNIDADES  →  api/unidades.php
──────────────────────────────────────

GET    /api/unidades.php             → Lista todas las unidades ordenadas
GET    /api/unidades.php?id=X        → Obtiene una unidad por ID
POST   /api/unidades.php             → Crea una unidad
  Body: { nombre, propietario, email, coeficiente, ascensor, orden }
PUT    /api/unidades.php?id=X        → Edita una unidad
  Body: igual al POST
DELETE /api/unidades.php?id=X        → Elimina una unidad

Validaciones:
  - La suma de coeficientes de todas las unidades no puede superar 1.0000.
  - Para calcular la liquidación, la suma debe ser exactamente 1.0000 (±0.001).

──────────────────────────────────────
5.2 GASTOS FIJOS  →  api/gastos_fijos.php
──────────────────────────────────────

GET    /api/gastos_fijos.php         → Lista gastos activos con sus unidades
POST   /api/gastos_fijos.php         → Crea un gasto fijo
  Body: { concepto, importe, division, unidades: [id, id, ...] }
  division: "coeficiente" | "partes_iguales"
PUT    /api/gastos_fijos.php?id=X    → Edita (reemplaza unidades asociadas)
  Body: igual al POST
DELETE /api/gastos_fijos.php?id=X    → Baja lógica (activo=0)

──────────────────────────────────────
5.3 GASTOS ESPORÁDICOS  →  api/gastos_esporadicos.php
──────────────────────────────────────

GET    /api/gastos_esporadicos.php?periodo=YYYYMM  → Lista del período
POST   /api/gastos_esporadicos.php                 → Crea gasto del período
  Body: { periodo, concepto, importe, division, unidades: [id, ...] }
  Nota: al agregar un gasto esporádico se borra la liquidación del período
        (obliga a recalcularla).
DELETE /api/gastos_esporadicos.php?id=X            → Elimina (también borra liquidación del período)

──────────────────────────────────────
5.4 LIQUIDACIÓN  →  api/liquidacion.php
──────────────────────────────────────

Nota: todas las operaciones de este endpoint son sobre la liquidación
      tipo='ordinaria' del período (filtro explícito en las 3 queries).
      Nunca tocan las liquidaciones tipo='extraordinaria' del mismo período
      (ver 5.4bis).

GET    /api/liquidacion.php?periodo=YYYYMM  → Obtiene liquidación ordinaria calculada
  Responde: { id, periodo, total_general, unidades: [ { nombre, lineas, total, ... } ] }
  Retorna null si no existe liquidación ordinaria para ese período.

POST   /api/liquidacion.php                 → Calcula (o recalcula) la liquidación ordinaria
  Body: { periodo: "YYYYMM" }
  Proceso:
    1. Verifica que la suma de coeficientes = 1.0000
    2. Para cada gasto fijo/esporádico que aplica a la unidad, calcula la parte:
       - division='coeficiente'    → importe × (coeficiente_unidad / coeficiente_total_afectado)
       - division='partes_iguales' → importe / cantidad_unidades_afectadas
    3. Suma el saldo_anterior (del período anterior) al total
    4. Borra la liquidación ordinaria anterior del período si existía
    5. Inserta en: liquidaciones (tipo='ordinaria'), liquidacion_detalle, liquidacion_lineas, cuenta_corriente
    6. En cuenta_corriente usa ON DUPLICATE KEY UPDATE sobre 'deuda' y 'saldo_anterior'
       para no pisar pagos (pagado) ni cargos extraordinarios ya registrados

DELETE /api/liquidacion.php?periodo=YYYYMM  → Borra la liquidación ordinaria del período
  No borra la fila de cuenta_corriente: solo pone deuda=0 (preserva pagado
  y extraordinario ya registrados). Tampoco toca las extraordinarias del período.

──────────────────────────────────────
5.4bis LIQUIDACIÓN EXTRAORDINARIA  →  api/liquidacion_extraordinaria.php
──────────────────────────────────────

GET    /api/liquidacion_extraordinaria.php               → Lista todas las extraordinarias
GET    /api/liquidacion_extraordinaria.php?periodo=YYYYMM→ Lista las del período
  Responde: [ { id, periodo, titulo, calculada_en, total_general, cant_unidades, cant_enviados } ]

GET    /api/liquidacion_extraordinaria.php?id=X          → Detalle completo
  Responde: { id, periodo, titulo, total_general, unidades: [ { nombre, propietario,
             email, total, mail_enviado, lineas: [...] } ] }
  Retorna null si no existe o no es de tipo extraordinaria.

POST   /api/liquidacion_extraordinaria.php  → Emite una liquidación extraordinaria
  Body: { titulo, periodo: "YYYYMM", conceptos: [ { concepto, importe, division,
          unidades: [id, ...] }, ... ] }
  Proceso:
    1. Por cada concepto, reparte el importe entre las unidades elegidas
       (misma lógica de coeficiente/partes_iguales que la liquidación ordinaria)
    2. Solo quedan afectadas las unidades con subtotal > 0
    3. Inserta en: liquidaciones (tipo='extraordinaria', titulo), liquidacion_detalle,
       liquidacion_lineas (tipo='extraordinario')
    4. En cuenta_corriente SUMA el cargo sobre la columna 'extraordinario'
       (ON DUPLICATE KEY UPDATE extraordinario = extraordinario + VALUES(...));
       si no existía la fila del período, la crea con deuda=0 y el saldo_anterior
       correspondiente (misma cadena de saldo que usa la ordinaria)
    Todo dentro de una transacción.

DELETE /api/liquidacion_extraordinaria.php?id=X  → Anula una extraordinaria
  Resta de cuenta_corriente.extraordinario el monto que había sumado, y borra
  liquidaciones/liquidacion_detalle/liquidacion_lineas (cascada por FK).

El envío de los mails de una extraordinaria reutiliza api/enviar_mail.php
(mismo endpoint que la liquidación ordinaria) pasando el detalle_id y un
asunto/cuerpo propios armados en el asistente de "Nueva extraordinaria"
del frontend — no usa la plantilla_mail mensual.

──────────────────────────────────────
5.5 CAJA  →  api/caja.php
──────────────────────────────────────

GET    /api/caja.php                        → Lista paginada de movimientos
  Parámetros opcionales: tipo, anio, mes, pagina (50 por página)
  Responde: { movimientos, saldo_total, pagina, total_pags, total_filas }
  saldo_total: saldo acumulado global (sin filtros)

POST   /api/caja.php                        → Registra un movimiento
  Body: { fecha, tipo, concepto, importe, unidad_id?, periodo?, notas? }
  - tipo: "ingreso" | "egreso"
  - Si tipo=ingreso + unidad_id + periodo: actualiza cuenta_corriente.pagado
  - Todo el proceso corre dentro de una transacción

DELETE /api/caja.php?id=X                   → Elimina un movimiento
  - Si era ingreso con unidad+período: recalcula cuenta_corriente.pagado

Función interna actualizarPagadoCC(unidad_id, periodo):
  → Suma todos los ingresos de caja para esa unidad y período
  → Actualiza cuenta_corriente.pagado con esa suma

──────────────────────────────────────
5.6 CUENTA CORRIENTE  →  api/cuenta_corriente.php
──────────────────────────────────────

GET /api/cuenta_corriente.php?periodo=YYYYMM
  → Resumen de todas las unidades para ese período
  → Incluye: deuda, saldo_anterior, pagado, saldo_final

GET /api/cuenta_corriente.php?unidad_id=X
  → Historial completo de una unidad (todos los períodos, desc)

GET /api/cuenta_corriente.php?unidad_id=X&periodo=YYYYMM
  → Devuelve el saldo_final del período inmediatamente anterior
  → Usado por liquidacion.php para calcular el saldo arrastrado

──────────────────────────────────────
5.7 ENVIAR MAIL  →  api/enviar_mail.php
──────────────────────────────────────

POST /api/enviar_mail.php
  Body: { detalle_id, asunto, cuerpo }
  → Envía mail al propietario de la unidad con la liquidación
  → Marca mail_enviado=1 en liquidacion_detalle

──────────────────────────────────────
5.8 EXPORTAR  →  api/exportar_*.php
──────────────────────────────────────

GET /api/exportar_caja.php?anio=YYYY&mes=MM
  → Descarga Excel con movimientos de caja del período

GET /api/exportar_cuenta_corriente.php?periodo=YYYYMM
  → Descarga Excel con estado de cuenta del período

──────────────────────────────────────
5.9 BACKUP  →  api/backup.php
──────────────────────────────────────

GET /api/backup.php
  → Genera y descarga un archivo .sql completo de toda la base de datos.
  → Nombre del archivo: edificio_backup_YYYYMMDD_HHMMSS.sql
  → Incluye: DROP TABLE IF EXISTS + CREATE TABLE + INSERT de cada tabla.
  → Las columnas GENERATED (como saldo_final) se omiten de los INSERT;
    MySQL las recalcula automáticamente al restaurar.

POST /api/backup.php  (multipart/form-data)
  → Campo: backup (archivo .sql)
  → Restaura toda la base de datos a partir del archivo recibido.
  → Deshabilita FK_CHECKS durante la ejecución para respetar el orden.
  → Responde: { ok: true, data: { sentencias: N } }
  → Límite de tamaño: 50 MB.

  ADVERTENCIA: esta operación reemplaza todos los datos existentes.
  No se puede deshacer. Usar solo con un backup previamente exportado
  desde este mismo sistema.

────────────────────────────────────────────────────────────────────────────────
7. FLUJO OPERATIVO MENSUAL
────────────────────────────────────────────────────────────────────────────────

Cada mes se sigue este flujo:

  1. (Opcional) Agregar gastos esporádicos del mes
     → Sección "Gastos Esporádicos" → nuevo gasto → asignar unidades

  2. Calcular la liquidación
     → Sección "Liquidación" → seleccionar período → "Calcular"
     → El sistema genera el detalle por unidad y crea los registros
       de cuenta_corriente con el saldo arrastrado del mes anterior

  3. Enviar liquidaciones por mail
     → En la pantalla de Liquidación → botón "✉ Mail" por cada unidad
     → Se usa PHPMailer con Gmail SMTP

  4. Registrar pagos
     → Sección "Caja" → "Nuevo movimiento"
     → tipo=ingreso, seleccionar unidad y período correspondiente
     → El sistema actualiza automáticamente cuenta_corriente.pagado

  5. Controlar deudas
     → Sección "Cuenta Corriente" → seleccionar período
     → Se ve deuda, pagado y saldo final por cada unidad


────────────────────────────────────────────────────────────────────────────────
8. LÓGICA DE CÁLCULO DE EXPENSAS
────────────────────────────────────────────────────────────────────────────────

Para cada gasto que aplica a una unidad:

  Si division = 'coeficiente':
    coef_afectado = suma de coeficientes de las unidades que tienen ese gasto
    parte_unidad  = importe × (coeficiente_unidad / coef_afectado)

  Si division = 'partes_iguales':
    parte_unidad  = importe / cantidad_unidades_afectadas

  Total unidad = suma de todas las partes + saldo_anterior

  saldo_anterior = saldo_final del último período registrado en cuenta_corriente

  El campo saldo_final en cuenta_corriente es una columna GENERADA:
    saldo_final = saldo_anterior + deuda - pagado


────────────────────────────────────────────────────────────────────────────────
9. CORRECCIONES APLICADAS (junio 2026)
────────────────────────────────────────────────────────────────────────────────

Se corrigieron los siguientes problemas que causaban que movimientos de caja
"a veces no se guardaran":

  1. Sin transacción en POST de caja.php
     Si el INSERT en caja tenía éxito pero actualizarPagadoCC fallaba,
     el movimiento quedaba en la base pero cuenta_corriente sin actualizar.
     FIX: beginTransaction() / commit() / rollBack() alrededor de ambas ops.

  2. Sin try/catch en el endpoint POST
     Cualquier error de BD devolvía una página HTML de PHP en vez de JSON.
     El frontend recibía un SyntaxError y no podía mostrar el error real.
     FIX: try/catch devuelve json_err() con el mensaje del error.

  3. Doble clic en "Guardar"
     Sin protección contra doble clic, dos requests simultáneos podían
     crear movimientos duplicados o estados inconsistentes.
     FIX: el botón se deshabilita durante el envío (finally lo reactiva).

  4. unidad_id enviado como string vacío
     $b['unidad_id'] ?? null no normalizaba "" a null.
     FIX: !empty($b['unidad_id']) ? (int)$b['unidad_id'] : null

  5. Sin validación del campo tipo
     Cualquier string se aceptaba como tipo de movimiento.
     FIX: in_array($b['tipo'], ['ingreso', 'egreso'], true)

  6. Sin validación del formato de período
     Un período malformado hacía que actualizarPagadoCC no encontrara
     registros pero tampoco fallaba, de forma silenciosa.
     FIX: preg_match('/^\d{4}(0[1-9]|1[0-2])$/', $periodo)


────────────────────────────────────────────────────────────────────────────────
10. NOTAS TÉCNICAS
────────────────────────────────────────────────────────────────────────────────

- La conexión PDO usa ERRMODE_EXCEPTION: cualquier error de BD lanza una
  excepción, que es capturada por los try/catch de cada endpoint.

- El DELETE de gastos_fijos es lógico (activo=0), no físico. Esto preserva
  el historial de liquidaciones anteriores que referenciaban ese gasto.

- La tabla cuenta_corriente usa ON DUPLICATE KEY UPDATE al calcular la
  liquidación: si ya existe un registro para unidad+período, solo actualiza
  deuda y saldo_anterior, sin tocar el campo pagado (preserva cobros ya
  registrados).

- Al agregar o eliminar un gasto esporádico, la liquidación del período se
  borra automáticamente para forzar su recálculo.

- La exportación a Excel requiere la librería PhpSpreadsheet o similar
  (ver los archivos exportar_*.php).

- El mail se envía con PHPMailer usando TLS en el puerto 587 de Gmail.
  Se requiere una "contraseña de aplicación" de Google (no la contraseña
  normal de la cuenta).
